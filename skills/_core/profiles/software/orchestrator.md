Créer le skill projet qui pilote un cycle complet. Frontmatter exact, une clé par ligne : `name: factory-run` ; `description: Lance un cycle de l'usine logicielle (Planner → gate humaine sur la spec → Builder → Verifier avec boucle de correction) sur un besoin ou une spec approuvée.` ; `disable-model-invocation: true` ; `argument-hint: "<besoin | chemin d'une spec> [--models \"role=modele;...\"] [--autonomy gate|auto] [--ship <cible> | --no-ship] [--worktree]"`.

Le corps (rédigé intégralement, voix impérative, adapté à la stack) écrit en clair `H` = `<PY> .claude/harness/harness.py` (copie du noyau, Phase 4) et impose : **chaque sous-agent lancé est consigné** par `H factory-run record --run <run> --agent <nom> --duration-ms <ms> --tokens <n>` (le modèle consigné est celui du rôle), valeurs du bloc d'usage de l'outil Agent (sans durée : `H begin --run <run> --slot <nom>` juste avant l'agent ; sans tokens : omettre l'option ; une mesure manquante est journalisée `null` et signalée, jamais bloquante ; connue seulement après l'appel, elle complète la dernière entrée du slot par `H journal amend --run <run> --slot <nom> --duration-ms <ms> --tokens <n>`) ; `--output .harness/runs/verifier-<n>.md`, fichier où la sortie du Verifier est écrite telle quelle avec l'outil Write (jamais par stdin ni via le shell : backticks, `$`, apostrophes) ; `--dead` si l'agent est mort. Le champ `action` du JSON rendu dicte la suite ; ne jamais sauter un appel ni décider à la place du noyau. Déroulé pour la session principale :

1. **Entrée** (FR-01, BQ-07) : écrire `$ARGUMENTS` tel quel avec l'outil Write dans `.harness/runs/factory-run-arguments.txt` (jamais dans une ligne de commande shell : un besoin peut contenir guillemets, `$` ou backticks), puis `H factory-run start --arguments-file .harness/runs/factory-run-arguments.txt` ouvre le journal `.harness/runs/factory-run-<horodatage>.jsonl` et rend `mode` : `build` (spec `APPROUVEE`) → étape 3 ; `approve` (spec `PROPOSEE`, ou `BLOQUEE` entièrement répondue : intégrer les réponses) → gate d'approbation de l'étape 2, puis étape 3 ; `plan` → traiter `need` comme le besoin. Exit 1 : spec `BLOQUEE` avec des questions sans réponse, ou spec `LIVREE` ; afficher le message de stderr (il cite le fichier `STOP-*.md`) et s'arrêter. Il retire de `$ARGUMENTS` `--models "role=modele;…"` (rôles `factory.planner`, `factory.builder`, `factory.verifier`, ce cycle seulement ; rôle ou valeur inconnus → exit 2) et rend `models` : passer à chaque sous-agent le paramètre `model` du rôle quand `pass_param` est vrai, jamais pour `inherit`. Il retire aussi `--autonomy gate|auto` (AP-03, cette exécution seulement), `--ship <cible>`, `--no-ship`, `--deliver-only`, `--worktree` (WT-08 : un besoin passe d'abord par la phase Plan dans cette session, puis `H worktree create` et `H worktree transfer`, l'enfant `factory-run <spec> --ship <cible>` dans le worktree, l'attente par `H chain wait`, et `H worktree remove --merged` si la PR est mergée) et les options internes `--chained-from`, `--chain-id` ; la politique effective est rendue (`autonomy`) et transmise à tout skill enchaîné.
2. **Phase Plan et approbation** : lancer le sous-agent `factory-planner` avec le besoin ; écrire `specs/SPEC-<slug-du-besoin>.md` avec en tête `Statut : PROPOSEE` suivi, sur des lignes contiguës, de `Questions bloquantes : Q<n>, … | aucune`, `Périmètre fichiers : <globs>` (si la spec peut le borner), `Dépend de :`, `Priorité :` ; chaque question ouverte est `- Q<n> — <texte>` avec une ligne `Défaut :` (obligatoire hors question bloquante). Puis `H factory-run bind --run <run> --spec <spec>` et `H spec settle --run <run> --file <spec>` : en `auto`, une question bloquante sans réponse passe la spec à `BLOQUEE` et arrête le cycle (exit 1, STOP `blocked`), sinon chaque question non bloquante reçoit son `Défaut :` (`Réponse : … (défaut appliqué automatiquement)`, une seule décision `factory-run.questions` journalisée) ; en `gate`, poser les questions (gate `factory-run.questions`, options du brouillon). Approbation (gate `factory-run.approval` : approbation / itérer) : `H gate decide --run <run> --id factory-run.approval`, AskUserQuestion si `ask`, puis `H gate answer --run <run> --id factory-run.approval --answer "<option>"` (ou `--default`, ou `--headless` sans interaction possible → arrêt, exit 1) ; approuvée : `H spec set-status <spec> APPROUVEE`, sinon itérer. Ne jamais construire sans spec approuvée. Défauts en politique `auto` (AP-09, une ligne chacun, mot pour mot celle du catalogue) : `factory-run.profile` → premier profil du tampon — the first profile of the stamp is the first one retained at installation ; `factory-run.questions` → le `Défaut :` du Planner — the planner's declared default for each non-blocking question; nothing is invented, a blocking question blocks the spec ; `factory-run.approval` → approuver — roadmap 4.2: approved without waiting, a blocking question having blocked the spec before ; `factory-run.ship` → livrer et lancer ship-pr — roadmap 4.2: a green build is delivered when CH-02 holds.
3. **Phase Build** : `H activate --run <run> --skill factory-run --session "${CLAUDE_SESSION_ID}" --spec <spec>` active les hooks de périmètre (HK-05) ; lancer le sous-agent `factory-builder` (contexte frais) avec le chemin de la spec approuvée. En fin de cycle — succès, échec ou arrêt — `H deactivate --run <run> --session "${CLAUDE_SESSION_ID}"`. Tout arrêt (exit 1, message `STOP: … (see <fichier>)`) est final : afficher le message et s'arrêter, aucune commande de plus sur ce run.
4. **Phase Verify — boucle de correction, 3 itérations maximum** : lancer un sous-agent `factory-verifier` (contexte vierge, indépendant du Builder) avec le chemin de la spec, consigner son bloc JSON, puis selon `action` :
   - `success` (FR-02 : `APPROVED` **et** `tests_passed` vrai) : sortir de la boucle ;
   - `fix` : relancer `factory-builder` avec la spec **et la liste complète des `issues` rendues** (fichier, sévérité, description) et la consigne de corriger sans régresser ; puis un nouveau Verifier ;
   - `relaunch` (FR-04) : relancer **une fois** l'agent mort ou à la sortie inexploitable, sans consommer d'itération ;
   - `fail` : **échouer explicitement** en publiant `reason` et les issues restantes — 3e itération non approuvée (FR-03) ou second échec d'un agent (FR-04). Ne jamais approuver par épuisement.

   **Un Verifier muet n'est pas un Verifier satisfait** : ne jamais traiter l'absence de verdict comme une approbation, ne jamais passer à la suite sur un verdict absent. Un cycle qui livre du code non vérifié parce que son vérificateur est tombé est pire qu'un cycle qui échoue.
5. **Rapport final** : fichiers modifiés (`git status`), résultat des tests, verdict, nombre d'itérations, chemin du journal, prochaine action. Sur `success` la spec est passée à `LIVREE` par le noyau. Livraison (CH-02, gate `factory-run.ship`, sauf `--no-ship`) : `H factory-run deliver --run <run> [--trailer "<ligne d'attribution>"]` crée au besoin la branche `factory/<slug>`, commite `feat(factory): <titre>` (jamais de push) et rend `ship_args` ; sans `--deliver-only`, invoquer par l'outil Skill `ship-pr <ship_args>` ; condition fausse → rien n'est commité, la raison est journalisée, suggérer `/ship-pr <cible>`. Hors livraison, ne pas commiter à la place de l'utilisateur.
