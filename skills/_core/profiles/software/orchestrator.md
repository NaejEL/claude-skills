Créer le skill projet qui pilote un cycle complet. Frontmatter exact, une clé par ligne : `name: factory-run` ; `description: Lance un cycle de l'usine logicielle (Planner → gate humaine sur la spec → Builder → Verifier avec boucle de correction) sur un besoin ou une spec approuvée.` ; `disable-model-invocation: true` ; `argument-hint: "<besoin | chemin d'une spec approuvée> [--models \"role=modele;...\"]"`.

Le corps (rédigé intégralement, voix impérative, adapté à la stack) écrit en clair `H` = `<PY> .claude/harness/harness.py` (copie du noyau, Phase 4) et impose : **chaque sous-agent lancé est consigné** par `H factory-run record --run <run> --agent <nom> --duration-ms <ms> --tokens <n>` (le modèle consigné est celui du rôle), valeurs du bloc d'usage de l'outil Agent (sans durée : `H begin --run <run> --slot <nom>` juste avant l'agent ; sans tokens : omettre l'option ; une mesure manquante est journalisée `null` et signalée, jamais bloquante ; connue seulement après l'appel, elle complète la dernière entrée du slot par `H journal amend --run <run> --slot <nom> --duration-ms <ms> --tokens <n>`) ; `--output .harness/runs/verifier-<n>.md`, fichier où la sortie du Verifier est écrite telle quelle avec l'outil Write (jamais par stdin ni via le shell : backticks, `$`, apostrophes) ; `--dead` si l'agent est mort. Le champ `action` du JSON rendu dicte la suite ; ne jamais sauter un appel ni décider à la place du noyau. Déroulé pour la session principale :

1. **Entrée** (FR-01) : écrire `$ARGUMENTS` tel quel avec l'outil Write dans `.harness/runs/factory-run-arguments.txt` (jamais dans une ligne de commande shell : un besoin peut contenir guillemets, `$` ou backticks), puis `H factory-run start --arguments-file .harness/runs/factory-run-arguments.txt` ouvre le journal `.harness/runs/factory-run-<horodatage>.jsonl` et rend `mode` : `build` (spec existante sous `specs/` dont la ligne de statut vaut `Statut : APPROUVEE`) → étape 3 ; `plan` → traiter `need` comme le besoin. Il retire de `$ARGUMENTS` l'option `--models "role=modele;…"` (rôles `factory.planner`, `factory.builder`, `factory.verifier`), valable pour ce cycle seulement (rôle ou valeur inconnus → exit 2), et rend `models` : passer à chaque sous-agent le paramètre `model` de l'outil Agent valant le `model` de son rôle quand `pass_param` est vrai, jamais pour `inherit`.
2. **Phase Plan (gate humaine)** : lancer le sous-agent `factory-planner` avec le besoin ; à son retour, poser à l'utilisateur les *Questions ouvertes* du brouillon (gate `factory-run.questions`, options du brouillon) ; intégrer les réponses, écrire `specs/SPEC-<slug-du-besoin>.md` avec en tête `Statut : PROPOSEE` ; présenter la spec à l'utilisateur et demander son approbation explicite (gate `factory-run.approval` : approbation / itérer) ; approuvée, passer le statut à `APPROUVEE` ; sinon itérer sur la spec. Chaque gate : `H gate decide --run <run> --id <id>` (rend `decision`, `options`, `headless`), AskUserQuestion, puis `H gate answer --run <run> --id <id> --answer-file .harness/runs/gate-answer.txt` (réponse écrite par Write ; `factory-run.approval` : l'option mot pour mot, `reask` rendu → reposer la question). **Sans interaction possible (headless), `H gate answer --run <run> --id <id> --headless` : pour `factory-run.questions`, retenir les réponses par défaut du brouillon ; pour `factory-run.approval`, approuver ; mais une question marquée bloquante sans réponse par défaut arrête le cycle (spec laissée `PROPOSEE`).** Ne jamais construire sans spec approuvée.
3. **Phase Build** : lancer le sous-agent `factory-builder` (contexte frais) avec le chemin de la spec approuvée.
4. **Phase Verify — boucle de correction, 3 itérations maximum** : lancer un sous-agent `factory-verifier` (contexte vierge, indépendant du Builder) avec le chemin de la spec, consigner son bloc JSON, puis selon `action` :
   - `success` (FR-02 : `APPROVED` **et** `tests_passed` vrai) : sortir de la boucle ;
   - `fix` : relancer `factory-builder` avec la spec **et la liste complète des `issues` rendues** (fichier, sévérité, description) et la consigne de corriger sans régresser ; puis un nouveau Verifier ;
   - `relaunch` (FR-04) : relancer **une fois** l'agent mort ou à la sortie inexploitable, sans consommer d'itération ;
   - `fail` : **échouer explicitement** en publiant `reason` et les issues restantes — 3e itération non approuvée (FR-03) ou second échec d'un agent (FR-04). Ne jamais approuver par épuisement.

   **Un Verifier muet n'est pas un Verifier satisfait** : ne jamais traiter l'absence de verdict comme une approbation, ne jamais passer à la suite sur un verdict absent. Un cycle qui livre du code non vérifié parce que son vérificateur est tombé est pire qu'un cycle qui échoue.
5. **Rapport final** : fichiers modifiés (`git status`), résultat des tests, verdict, nombre d'itérations, chemin du journal, prochaine action suggérée (revue du diff par l'utilisateur ; ne pas commiter à sa place).
