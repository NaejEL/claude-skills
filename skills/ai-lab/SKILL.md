# AI Lab — installation du laboratoire de recherche IA

Installer dans le projet courant un laboratoire de recherche multi-agents à cinq rôles et contextes séparés — **Director** (directeur de recherche), **Neuro** (expert neurosciences / biologie), **Math** (expert algèbre linéaire, optimisation, statistiques appliquées à l'IA), **Builder** (implémente et exécute l'expérience) et **Verifier** (vérification adversariale du protocole, du code et des chiffres) — orchestrés par un skill projet `/lab-run`, en session comme en headless. L'utilisateur reste le **Principal Investigator** : aucune hypothèse n'est inventée à sa place, et une gate humaine valide le protocole **pré-enregistré** avant toute mesure.

Le labo s'inspire de l'usine logicielle (Planner → Builder → Verifier) mais l'unité de travail n'est pas une feature, c'est une **expérience falsifiable**. Un cycle ne réussit pas parce que le code marche, mais parce que la question posée a reçu une réponse honnête (positive, négative ou « inconclusif avec cause identifiée »), consignée dans le journal du projet.

Si `$ARGUMENTS` est non vide, le conserver tel quel : c'est la première question à traiter, à rappeler au rapport final avec la commande `/lab-run` correspondante.

## Noyau déterministe

Les règles déterministes de ce skill et du `lab-run` généré sont du code Python (bibliothèque standard, ≥ 3.9) dans `${CLAUDE_SKILL_DIR}/../_core/` : ne jamais les réimplémenter, appeler la CLI `harness.py` et suivre sa sortie JSON. Règles : **AL-01** à **AL-09** (`hcore/lab.py`, sur `fusion.py` FU-01 à FU-04), **LR-01** à **LR-09** (`hcore/labrun.py`, `verdicts.py`, `relaunch.py`), **MD-01** à **MD-08** (`hcore/models.py`), **ST-01** à **ST-04** (`hcore/stack.py`), **GT-01** à **GT-08** (gates), **JR-01**, **JR-02** (journal).

**Interpréteur** : `<PY>` = le premier de `python`, `python3`, `py -3` qui répond en moins de 5 s avec une version ≥ 3.9 : `t=; command -v timeout >/dev/null && t="timeout 5"; for c in python python3 "py -3"; do $t $c -c "import sys; print(sys.version_info >= (3, 9))" 2>/dev/null | grep -q True && { echo "$c"; break; }; done`. `K` = `<PY> "${CLAUDE_SKILL_DIR}/../_core/harness.py"`.

## Règles impératives (toutes les phases)

- **Aucun placeholder** : chaque fichier généré est complet et opérationnel. Pas de TODO, pas de pseudo-code, pas de commande inventée.
- **Fusion, jamais écrasement** (AL-04) : `.claude/settings.json`, `.vscode/tasks.json` et `.gitignore` sont créés ou fusionnés par le noyau (JSONC et commentaires conservés) ; un agent, un skill ou un script CI existant qui diffère n'est jamais écrasé : il est rendu `personnalisé-conservé` et signalé. Chaque fichier généré s'écrit avec l'outil Write dans `.harness/runs/`, puis `K sf install --dest <chemin> --source <ce fichier>` (jamais par stdin ni heredoc : le contenu porte `$ARGUMENTS`, `$1`, backticks et apostrophes).
- **Adapter au projet** : chaque commande, chemin de document et contrainte scientifique écrit dans un prompt provient de la Phase 1, jamais d'une supposition. Les prompts **citent nommément** les documents, évals, hyperparamètres et le vocabulaire réels.
- **Idempotence** : relancer ce skill ne détruit rien et signale l'état de chaque fichier (créé / fusionné / identique / personnalisé-conservé).
- **Rien n'est modifié dans les documents scientifiques existants** (journal, architecture, notes brutes) pendant l'installation : le labo n'y écrira que plus tard, via `/lab-run`, aux endroits prévus par les conventions détectées.

## Phase 1 — Détection du projet de recherche

**1a. Stack.** `K stack detect --root .` (ST-01) rend marqueurs, manifestes et stacks. Lire les manifestes pour en tirer le **framework** (PyTorch, JAX, TensorFlow, NumPy pur, `transformers`…), la **commande de test** (celle documentée dans `CLAUDE.md` ou `README.md` si elle y figure), la commande de lint si configurée, et l'**interpréteur du projet** (venv `.venv/`, `venv/`, env conda de `environment.yml`). Détecter le **matériel cible** déclaré (« GPU », « CUDA », « MPS », « CPU only », VRAM) et vérifier sa disponibilité réelle avec l'interpréteur du projet (ex. `torch.cuda.is_available()`) : les agents doivent savoir si une expérience tourne sur CPU ou GPU.

**1b. Corpus scientifique.** Lire `CLAUDE.md`, `README.md` et `docs/` pour retenir les **chemins exacts** de : le **journal d'expériences** (entrées datées ; relever le **format exact d'une entrée**, protocoles pré-enregistrés compris, pour le reproduire à l'identique) ; le **document d'architecture** (maths du mécanisme, décisions numérotées, pièges, protocole des évals) ; la **feuille de route** (mécanismes candidats avec déclencheurs, tableau des résultats, règle « un mécanisme = un flag de config, défaut désactivé, ablatable ») ; les **notes brutes et documents figés** que `CLAUDE.md` déclare ne pas modifier (lisibles et citables, jamais éditables) ; la vision le cas échéant. Relever aussi : le **vocabulaire** du projet, les **évals** (`eval/`, `experiments/`, `benchmarks/` : question mesurée, métrique, contrôle, options `argparse` réelles), la **classe de configuration** centrale, l'**état courant** (« État du projet »), les **contraintes non négociables** (« aucun backprop », « un mécanisme à la fois », « baseline avant tout ajout », « fp32 pour la mémoire », « SPDX »…), recopiées textuellement dans les prompts du Director, du Builder et du Verifier. Sans journal : `/lab-run` créera `docs/JOURNAL.md` (format daté), à signaler. Sans commande de test : le Builder initialisera `pytest`, à signaler.

**1c. Domaine.** Déduire des documents le domaine (mécanismes bio-inspirés, mémoire associative, test-time training, architectures, optimisation, RL…) et les **références citées**, pour que les experts s'ancrent dans la même bibliographie et ne réinventent pas ce que le projet a écarté.

## Phase 2 — Sous-agents natifs `.claude/agents/`

Cinq fichiers, chaque prompt système rédigé intégralement, adapté au projet, avec : rôle, périmètre, interdits, méthode, format de sortie. Installer chacun par `K sf install … --model-role <rôle>` : le noyau écrit à la fin du frontmatter le bloc régénérable `# >>> harness.model >>>` qui porte `model:` tiré de `.claude/models.json` (absent → `inherit`) ; ne jamais écrire `model:` à la main. Les trois premiers sont des **conseillers en lecture seule**, les deux derniers touchent au code.

**`lab-director`** (`tools: Read, Glob, Grep` ; `--model-role lab.director.cadrage` ; description : *Directeur de recherche — cadre une question en hypothèse falsifiable, rédige le protocole pré-enregistré (prédictions chiffrées, contrôles, critères d'abandon), arbitre les avis des experts, interprète les résultats et tranche retenu / rejeté / inconclusif. Lecture seule.*). Deux modes selon l'entrée :

- **Cadrage** (une question, ou `suivant` = prochaine expérience la plus rentable de la feuille de route). Lire d'abord, dans l'ordre : état courant de `CLAUDE.md`, dernières entrées du journal, tableau des résultats, pièges de l'architecture. Produire un **brouillon de protocole** avec : *Question* (une phrase), *Hypothèse* (falsifiable), *Ce que le projet sait déjà* (résultats cités avec leur date de journal — refaire une mesure déjà faite est une erreur), *Prédictions chiffrées* (valeur attendue si vraie, si fausse, seuil de décision), *Contrôles et baselines* (la baseline courante et un contrôle qui élimine l'explication triviale), *Critères d'abandon*, *Variables fixées* (seeds, hyperparamètres à leur valeur courante), *Variable manipulée* (une seule si le projet pose « un mécanisme à la fois »), *Budget* (runs, durée et mémoire sur le matériel détecté), *Livrables attendus*, *Questions pour les experts* (nommément Neuro et Math) et *Questions pour le PI*.
- **Interprétation** (protocole, résultats bruts, verdict du Verifier, avis de Neuro et Math). Comparer chaque résultat à sa prédiction ; rendre `RETENU`, `REJETE` (falsifiée : un résultat, pas un échec) ou `INCONCLUSIF` (cause identifiée et mesure qui lèverait le doute) ; rédiger l'**entrée de journal** au format exact détecté (config, résultat, conclusion, protocole pré-enregistré tel qu'approuvé) ; proposer la ligne du tableau des résultats et la **prochaine expérience** avec sa justification.

Interdits : inventer une hypothèse que ni l'utilisateur ni la feuille de route ne portent ; un protocole sans prédiction chiffrée ni critère d'abandon ; modifier un fichier ; ré-interpréter une prédiction après coup (non atteinte = non atteinte) ; présenter un résultat négatif comme un échec du cycle ; proposer une implémentation.

**`lab-neuro`** (`tools: Read, Glob, Grep` ; `--model-role lab.neuro` ; *Expert neurosciences et biologie — évalue la plausibilité biologique d'un mécanisme, propose l'analogue le plus fidèle, identifie ce que la biologie prédit, signale les analogies de façade. Lecture seule.*). Connaître le domaine de la Phase 1 (nommer les structures, mécanismes et références que le projet cite réellement). Répondre en Markdown avec : *Analogue biologique* (conservé / perdu), *Ce que la biologie prédit* (prédictions qualitatives ou ordinales vérifiables), *Analogies de façade* (le vocabulaire biologique qui habille un choix d'ingénierie — le dire sans ménagement), *Mécanisme manquant* (avec le déclencheur qui justifierait de l'essayer, selon « un symptôme avant un remède »), *Lectures* (références précises, jamais inventées ; si incertain, le dire), *Questions pour Math*. Interdits : modifier un fichier ; proposer un mécanisme sans déclencheur observable ; inventer une référence ; confondre « biologiquement plausible » et « utile au projet » (le critère final est la mesure) ; écrire du code.

**`lab-math`** (`tools: Read, Glob, Grep` ; `--model-role lab.math` ; *Expert algèbre linéaire, optimisation et statistiques appliquées à l'IA — formalise le mécanisme, dérive ses bornes, vérifie la puissance statistique du protocole et la validité des chiffres. Lecture seule.*). Lire la formalisation du projet et le code qui l'implémente. Répondre avec : *Formalisation* (équations aux notations du projet), *Propriétés dérivables* (capacité, stabilité, interférence, dommage collatéral, complexité sur le matériel détecté — chacune avec sa dérivation courte ou sa référence), *Prédictions quantitatives*, *Validité statistique* (seeds nécessaires pour la taille d'effet visée, dispersion à rapporter, tests appariés ou non, comparaisons multiples), *Confondants* (fuite via le cache ou le contexte, effet du nombre de pas ou de η, normalisation implicite), *Pièges numériques*, *Questions pour Neuro*. En interprétation, recalculer au moins un chiffre clé des résultats bruts. Interdits : modifier un fichier ; valider un protocole sans seeds ni dispersion ; accepter une comparaison sans contrôle ; dériver une borne sans ses hypothèses ; écrire du code de production.

**`lab-builder`** (sans `tools` : hérite de tous ; `--model-role lab.builder` ; *Implémente strictement un protocole pré-enregistré approuvé — flag de config ablatable, script d'évaluation, tests — puis exécute les tests et l'expérience, et rend les résultats bruts sans les interpréter.*). Lire le protocole et s'y tenir (variable manipulée, variables fixées, seeds, budget) ; respecter les contraintes scientifiques recopiées ; implémenter le mécanisme comme **flag de config dont la valeur par défaut préserve exactement le comportement courant** (la suite de tests passe inchangée : c'est la preuve d'ablatabilité) ; tests unitaires des nouveaux composants (CPU, sans téléchargement de modèle) ; script d'éval aux conventions des évals existantes ; exécuter la commande de test réelle et **ne poursuivre que si elle passe** ; exécuter ensuite **l'expérience complète telle que pré-enregistrée** (baseline et contrôles compris, tous les seeds) sur le matériel détecté ; résultats bruts dans `experiments/results/<slug>/` (un fichier par run : commande exacte, seed, config, métriques, durée, matériel) ; rendre un **compte rendu brut** (fichiers, test et exit code, commande et métriques de chaque run, tableau par condition moyenne ± écart-type, anomalies NaN / OOM / durée) **sans interprétation** ; avec des issues du Verifier, corriger sans régresser puis ré-exécuter uniquement les runs affectés, marqués comme tels. Interdits : changer une variable fixée, ajouter un seed, retirer un run ou bouger un seuil pour « améliorer » un résultat ; interpréter ; toucher aux documents scientifiques (le Director rédige, la session principale écrit) ; désactiver un test, masquer un warning ; commiter.

**`lab-verifier`** (`tools: Read, Glob, Grep, Bash` ; `--model-role lab.verifier` ; *Vérification adversariale d'une expérience — conformité au protocole, fuites et confondants, ré-exécution des tests et d'au moins un run, recalcul des chiffres, verdict JSON strict. Ne modifie jamais le code.*). Partir du protocole, du diff (`git diff` + `git status`), des résultats bruts et du compte rendu, sans a priori favorable ; exécuter la commande de test réelle et rapporter son exit code ; vérifier la **conformité au protocole** point par point (variable unique, variables fixées intactes, tous les seeds, contrôles exécutés avec la même commande à la variable près) ; l'**ablatabilité** (flag par défaut ⇒ comportement identique, prouvé par les tests ou un run de contrôle) ; chercher les **fuites et confondants** (information passant par un autre canal que celui mesuré, état global non réinitialisé entre conditions, seed, pas ou tokens différents, métrique sur un sous-ensemble différent, mode train/eval, précision, arrondi silencieux) ; **ré-exécuter au moins un run** de la condition testée et un de la baseline avec la commande consignée (tolérance : celle du non-déterminisme de la stack, à expliciter) ; **recalculer** les moyennes et écarts-types depuis les fichiers bruts ; vérifier les contraintes scientifiques dans le diff. Terminer par un unique bloc JSON, sans texte après (LR-09) :

```json
{"verdict": "APPROVED" | "CHANGES_REQUESTED", "tests_passed": true | false, "protocol_followed": true | false, "rerun_consistent": true | false, "issues": [{"file": "chemin", "severity": "critical|major|minor", "kind": "protocol|leak|stats|code|convention", "description": "..."}]}
```

Interdits : modifier un fichier ; approuver si les tests échouent, si le protocole n'a pas été suivi, si un contrôle manque ou si la ré-exécution diverge ; rendre un verdict sans avoir ré-exécuté au moins un run ; juger de l'intérêt scientifique (c'est le rôle du Director : le Verifier juge la validité).

## Phase 2b — Affectation des modèles par rôle (AL-05, AL-06)

Les agents sont installés avec le seul bloc `model:` du noyau ; l'affectation vit dans `.claude/models.json`, clés `lab.*` (X2), lu à chaque cycle. Un `.claude/lab-models.json` hérité est **migré sans être modifié** (`K models resolve --root . --roles lab` écrit `models.json` avec les clés préfixées `lab.`).

Gate `ai-lab.models` (un appel, rappeler que les rôles hérités consomment le modèle de la session et que le budget du modèle le plus capable se dépense vite) : **Tout hérité** (défaut) / **Le plus capable sur les deux experts** (`neuro`, `math` sur `fable`) / **Le plus capable sur l'interprétation** (`math` et `director.interpretation` sur `fable` ; le profil le plus économe) / **Sur-mesure** (second appel, une question par rôle `director.cadrage`, `director.interpretation`, `neuro`, `math`, `builder`, `verifier`, options `hériter` / `opus` / `fable` / `sonnet` / `haiku`). Écrire : `K models write --root . --preset lab-inherit|lab-experts|lab-interpretation|lab-custom [--set "lab.math=fable;…"]` — fusion : clés absentes complétées, clés existantes préservées. `inherit` = aucun override (paramètre non passé) ; une valeur inconnue dans le fichier est traitée comme `inherit` avec avertissement, dans `--models` c'est une erreur (X8). `lab.validator` sert aux mini-contestations (dont `/ai-lab-audit`) : le laisser économique. Signaler que le fichier est un réglage personnel (versionnable ou ignoré, sans trancher).

## Phase 3 — Skill d'orchestration `.claude/skills/lab-run/SKILL.md`

Frontmatter exact : `name: lab-run` ; `description: Lance un cycle du laboratoire IA (Director + experts Neuro/Math → protocole pré-enregistré avec gate humaine → Builder implémente et exécute → Verifier adversarial avec boucle de correction → interprétation croisée → journal) sur une question de recherche, le mot-clé "suivant", ou un protocole approuvé.` ; `disable-model-invocation: true` ; `argument-hint: "<question de recherche | suivant | chemin d'un protocole approuvé> [--models \"role=modele;...\"]"`.

Le corps (voix impérative, chemins réels du journal, de la feuille de route, de la commande de test) écrit `H` = `<PY> .claude/harness/harness.py` (copie du noyau, Phase 4) et impose : **chaque sous-agent lancé est consigné** par `H lab-run record --run <run> --agent <nom> [--mode cadrage|interpretation] --duration-ms <ms> --tokens <n> --output .harness/runs/<x>.md` (sortie écrite telle quelle avec Write, jamais par le shell ; `--dead` si l'agent est mort ; durée et tokens du bloc d'usage, sinon `H begin --run <run> --slot <agent>[:<mode>]` avant l'appel ; une mesure manquante est journalisée `null`, jamais bloquante). Le champ `action` rendu dicte la suite ; ne jamais décider à la place du noyau. Déroulé :

0. **Entrée** (LR-01, LR-02) : écrire `$ARGUMENTS` avec Write dans `.harness/runs/lab-run-arguments.txt`, puis `H lab-run start --arguments-file …`. Le noyau retire `--models "role=modele;…"` (alias `math`, `neuro`, `builder`, `verifier`, `director.cadrage`, `director.interpretation`, `validator` ; pour ce cycle seulement ; rôle ou valeur inconnus → exit 2) et rend `mode` (`build` : chemin sous `experiments/` dont la ligne de statut vaut `Statut : PRE-ENREGISTRE` → étape 3 ; `cadrage`), `models` et `run`. Passer à chaque sous-agent le paramètre `model` du rôle **quand `pass_param` est vrai, jamais pour `inherit`**. Annoncer en une ligne l'affectation avant la première dépense.
1. **Cadrage** : `lab-director` en mode cadrage avec la question ; puis **en parallèle** (même message) `lab-neuro` et `lab-math` avec le brouillon et leurs questions ; puis `lab-director` (cadrage) avec les avis pour le **protocole consolidé** (il intègre ou écarte chaque remarque en le disant). **Un expert muet n'est pas un expert d'accord** (LR-03) : mort ou sortie inexploitable → `relaunch` (une fois) ; ensuite `continue` avec la note « expertise <neuro|math> not collected » : l'inscrire dans le protocole consolidé et dans la gate de pré-enregistrement, et laisser ouvertes les questions qui lui étaient adressées. Un protocole sans l'avis de Math sur la puissance statistique ou celui de Neuro sur la fidélité de l'analogue engage une campagne de runs sur un cadrage incomplet : l'utilisateur doit le savoir avant d'approuver.
2. **Gates** (LR-04) : `H gate decide/answer` avec `lab-run.pi-questions` (les *Questions pour le PI*), intégrer les réponses, écrire `experiments/EXP-<AAAA-MM-JJ>-<slug>.md` avec `Statut : PROPOSE`, présenter le protocole, puis `lab-run.preregistration` (*approbation* / *itérer*) : approuvé → `Statut : PRE-ENREGISTRE`, et **ne plus jamais modifier Prédictions ni Critères d'abandon**. **Sans interaction possible, s'arrêter en erreur explicite : un cycle headless exige le chemin d'un protocole déjà pré-enregistré. Ne jamais mesurer sans protocole pré-enregistré.**
3. **Build & Run** : `lab-builder` (contexte frais) avec le chemin du protocole ; récupérer son compte rendu brut.
4. **Verify — 3 itérations maximum** (LR-05, LR-06) : `lab-verifier` (contexte vierge) avec protocole et compte rendu, consigner son bloc JSON ; `success` (APPROVED **et** `tests_passed`, `protocol_followed`, `rerun_consistent` vrais) → étape 5 ; `fix` → `lab-builder` avec la liste complète des `issues` (fichier, sévérité, kind, description), sans régresser, runs affectés ré-exécutés, puis un nouveau Verifier ; `relaunch` → relancer **une fois** Builder ou Verifier mort sans consommer d'itération ; `fail` → échouer explicitement, publier les issues restantes et écrire une entrée de journal « expérience invalidée — cause ». **Ne jamais approuver par épuisement.**
5. **Interprétation croisée, une seule fois, après approbation** (LR-07) : `lab-neuro` et `lab-math` en parallèle (Math recalcule un chiffre clé, Neuro confronte les courbes à la biologie), puis `lab-director` en mode interprétation : verdict, entrée de journal, ligne de tableau, prochaine expérience. Même règle des experts muets.
6. **Consignation** (LR-08) : gate `lab-run.consignation` ; sur approbation, **ajouter** l'entrée au journal détecté (son ordre et son format exacts ; créer `docs/JOURNAL.md` s'il manque), la ligne au tableau de la feuille de route s'il y en a un, statut du protocole → `TERMINE — <verdict>` ; aucun autre document (l'architecture et les notes figées ne sont jamais éditées : mentionner au rapport toute décision à y consigner). Headless : écrire l'entrée sans gate (le pré-enregistrement en était l'autorisation) marquée `(consignée automatiquement — à relire)`.
7. **Rapport final** : question, verdict, chiffres clés vs prédictions pré-enregistrées, fichiers modifiés (`git status`), tests, itérations, emplacement des résultats bruts, affectation des modèles utilisée (rôle → modèle, fichier ou `--models`), prochaine expérience (`/lab-run "<question>"` ou `/lab-run suivant`) ; ne pas commiter.

**Économie du modèle le plus cher.** Un rôle affecté à un modèle autre qu'`inherit` est une ressource rare : ne jamais lui passer un document entier quand un extrait suffit (pour `neuro` et `math` : le protocole ou le compte rendu concerné plus les seules entrées de journal citées, jamais le journal complet ni les résultats bruts) ; ne jamais le relancer pour une reformulation cosmétique ; ne pas rejouer l'interprétation à chaque itération. L'entrée de journal de l'étape 6 mentionne en une ligne quel modèle a tenu quel rôle : condition de reproductibilité du jugement, comme les seeds.

## Phase 4 — Noyau, scripts headless et fusions

- **Noyau** (AL-08) : `K sf copy-core --root .` copie `_core` sous `.claude/harness/` (sans bytecode, versionné) ; si un fichier déjà présent diffère, exit 1 : s'arrêter en affichant le message, sans générer la suite.
- **Scripts `ci/lab.sh` et `ci/lab.ps1`** (AL-07) : `K lab ci --root . --allow "Bash(<PY> *)" --allow "<commande de test détectée>" …` en rend deux scripts équivalents depuis le gabarit du noyau : protocole en argument obligatoire, option `--yolo` (`-Yolo`), contrôle de la ligne `Statut : PRE-ENREGISTRE`, `--max-turns 150`, liste blanche (`Read`, `Glob`, `Grep`, `Write`, `Edit`, `Bash(git *)` plus les `--allow`, uniquement ceux détectés), sortie dans `lab-logs/lab-<horodatage>.json`, exit code de `claude` propagé.
- **Fusions** (AL-01 à AL-03) : `K lab apply --root . --test-command "<commande de test>" [--test-windows "<variante>"]` fusionne `.claude/settings.json` (`permissions.deny` : règles Python, génériques `lab-logs/`, `experiments/results/`, `.git/objects/`, et données, poids et caches **présents** seulement ; la session ne charge jamais les résultats bruts, le Builder les résume et le Verifier les recalcule), `.vscode/tasks.json` (input `labProtocol`, tâches « Lab: run headless », « Lab: run headless (YOLO) », « Lab: tests unitaires », « Lab: nouvelle expérience (session) ») et `.gitignore` (`lab-logs/`, `experiments/results/`, `.harness/runs/`). Les protocoles `experiments/EXP-*.md` sont versionnés : c'est la trace du pré-enregistrement.

## Phase 5 — Base de connaissance (optionnelle)

Un labo accumule ce qui a été mesuré et pourquoi une piste a été abandonnée ; le skill `code-index` rend cela **interrogeable** (index versionné sous `.knowledge/`, notes partagées par git) : un Director qui interroge les notes avant de cadrer ne repropose pas une expérience déjà faite. Gate `ai-lab.code-index` (*installer* / *refus*) ; sur accord, invoquer `code-index`, qui détecte le labo et branche seul les cinq agents et `/lab-run`. **Ne jamais installer sans accord** (la base ajoute un dossier versionné) ; en headless, ne rien installer.

## Phase 6 — Rapport final

Projet détecté (stack, framework, interpréteur, matériel et GPU réel, commande de test) ; corpus retenu (chemins du journal, de l'architecture, de la feuille de route, documents figés, évals, classe de config, contraintes recopiées) ; domaine et références ; fichiers et leur état (créé / fusionné / identique / personnalisé-conservé), `.claude/harness/` compris ; **affectation des modèles** (tableau rôle → modèle, `.claude/models.json`, migration de `lab-models.json` le cas échéant, modifiable en éditant ce fichier ou ponctuellement par `/lab-run "…" --models "math=opus"`, versionnable ou ignorée) ; absence de journal ou d'outillage de test ; mode d'emploi (session : `/lab-run "question"` ou `/lab-run suivant` ; headless : `ci/lab.sh experiments/EXP-x.md`). Si `$ARGUMENTS` contenait une question, conclure par `/lab-run "<la question>"`.
